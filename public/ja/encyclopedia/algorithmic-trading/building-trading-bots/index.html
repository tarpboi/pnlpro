トレーディングボットの作り方

トレーディングボットとは、ブローカーや取引所に接続し、マーケットデータを読み取り、いつ取引するかを判断して、自動的に注文を送るプログラムです。注文を出すだけのボットを作るのは簡単です。データが遅れたとき、接続が切れたとき、戦略が誤作動したときにも安全に振る舞うボットを作ることこそが、本当の仕事です。これはアルゴリズム取引のエンジニアリングの側面であり、標準的なアーキテクチャ、取引所APIの仕組み、そして実際のお金に触れる前にすべてのボットが備えるべき安全装置がその中心です。

要点

  • ボットは、データフィード、シグナル、リスク、執行、監視の各層に分けて設計します。
  • マーケットデータには WebSocket のストリームを使い、REST の呼び出しは注文と口座の確認に限定して、レート制限の範囲内に収めます。
  • APIキーには必要最小限の権限だけを与え、出金を無効にし、可能な場合はIPアドレス制限をかけます。
  • ハードなリスク上限と自動キルスイッチは必須です。ソフトウェアの障害は、どんな悪いトレードよりも速くお金を失わせることがあります。
  • まずドライランまたはペーパーモードで動かし、すべてをログに記録し、実運用での挙動をバックテストと比較してください。

ボットのアーキテクチャ

単純なスクリプトからプロのシステムまで、堅牢なボットの多くは同じ構成要素を共有しています。

層 役割 主な注意点
データフィード 価格、板情報、約定、口座の更新を受信する 再接続、欠損、古いデータ、タイムスタンプ
シグナル（戦略） データを目標ポジションや注文に変換する バックテストと同じロジック、先読みなし
リスク 送信前にすべての注文を上限と照合する ポジションサイズ、エクスポージャー、1日の損失、価格の妥当性チェック
執行 注文の発注・訂正・取消、約定の追跡 冪等性、部分約定、リトライ、レート制限
状態とストレージ ポジション、注文、残高の整合性を保つ 取引所と定期的に照合する
監視 アラート、ダッシュボード、ログ 何か問題があれば数分以内に把握する

層を分けておけば、同じシグナルのコードをバックテストと実運用の両方で再利用でき、リスク層を単独でテストできます。リスク層は、戦略が何を望んでいようと、あらゆる注文をブロックできるようにしておくべきです。執行層は、指値注文を送るだけの単純なものから、執行アルゴリズムで説明している分割ロジックのような複雑なものまでありえます。

取引所とブローカーのAPI

REST

REST API は標準的なWebリクエストを使います。リクエスト（注文の発注、残高の取得）を送り、レスポンスを受け取ります。シンプルですが、データのストリーミングには遅く、リクエストごとにレート制限の枠を消費します。

WebSocket

WebSocket の接続は開いたままの状態を保ち、約定、板の変化、注文の約定といった更新を、発生したそばからプッシュしてきます。リアルタイムでマーケットデータを受信する標準的な方法です。ボットは切断に対処し、再購読し、更新の取りこぼしがあった場合（通常はシーケンス番号で検出します）には、新しいスナップショットからローカルの板を再構築しなければなりません。

FIX

FIX プロトコルは機関投資家の取引で長く使われてきたメッセージング標準で、多くのブローカー、先物業者、一部の暗号資産取引所が、注文の入力とマーケットデータに使っています。実装はより複雑ですが、セッションが安定しており、メッセージ量が多い場合のオーバーヘッドが小さくなります。

認証

プライベートなエンドポイントでは通常、APIキーと、シークレットを使って計算した署名（多くは HMAC ベース）、それにタイムスタンプが必要です。サーバーの時計がずれるとリクエストが拒否されることがあるため、システムの時刻を同期させておいてください。ブロックチェーン上に構築された暗号資産取引所では、代わりにウォレットの秘密鍵で注文に署名する必要がある場合があります。

レート制限

取引所は、1秒または1分あたりに送れるリクエスト数を制限しています。多くの場合、重いリクエストほど多くを消費する「ウェイト」の予算という形をとります。上限を超えるとエラーが返され、違反を繰り返すと一時的に利用を禁止されます。良い実践例は次のとおりです。

  • マーケットデータは、REST のエンドポイントをポーリングするのではなく、WebSocket のストリームから取得する。
  • 自分の使用量を（多くはトークンバケット方式のカウンターで）追跡し、上限に達する前に速度を落とす。
  • レート制限のエラーが出たら、すぐにリトライせず、待ち時間を徐々に延ばしながらバックオフする。
  • 全注文を1回の呼び出しで取り消すなど、APIが対応していれば操作をまとめて行う。

APIキーのセキュリティ

APIキーが漏洩すると、口座が空になることもあります。キーは銀行のパスワードと同じように扱ってください。

  • 取引用のキーでは出金を無効にします。ボットが資金を出金する必要はめったにありません。
  • IPアドレスで制限し、自分のサーバーからしかキーが使えないようにします。
  • 最小権限の原則を守ります。 監視には読み取り専用のキーを、取引用のキーは必要な場所だけで使います。
  • キーをコードや公開リポジトリに絶対に書かないでください。 環境変数やシークレットマネージャーから読み込みます。
  • 取引所が対応していれば、ボットごとに資金を限定したサブアカウントを使います。
  • 出金権限付きのキーを求めるサードパーティのボットサービスや、ウォレットのシードフレーズを求めるツールには注意してください。暗号資産ウォレットのセキュリティと、Telegram 型のスワップボットについてはミームコインのトレーディングボットを参照してください。

キルスイッチとリスク上限

ソフトウェアの障害は壊滅的になることがあります。2012年8月1日、米国のマーケットメイカーである Knight Capital は欠陥のあるコードを本番環境に導入し、意図しない注文を大量に送信して、1時間足らずで約4億4,000万ドルを失い、救済を受けざるを得なくなりました。注文を再送し続けるループや、意図した10倍のサイズで取引してしまう単位の誤りなど、同じことの小規模版は個人のボットでも日常的に起きています。

すべてのボットには次のものが必要です。

  • 銘柄ごとおよび全体の最大ポジションサイズ。
  • 最大注文サイズと、現在の市場価格から大きく離れた注文を拒否するプライスカラー。
  • 注文を取り消し、必要に応じてポジションを解消し、人間が再起動するまでボットを停止させる1日の損失上限。
  • 想定をはるかに超える数の注文を送った場合にボットを停止させる注文レートの上限。
  • マーケットデータが一定時間更新されなかった場合に取引を停止する古いデータのチェック。
  • スマートフォンから作動させられる手動のキルスイッチ。

ドライラン、ペーパートレード、ログ

まずはシステム全体をドライランモードで動かします。注文を計算してログに記録するだけで、送信はしないモードです。次に、ペーパートレード、または取引所にテストネットがあればそこで動かします。テストネットは板が薄く約定の仕方も異なるなど、本番の市場とは挙動が違うことが多いため、パフォーマンスのテストではなくソフトウェアのテストとして扱ってください。

受信したデータ、シグナル、送信した注文、取引所の応答、約定、エラーなど、すべての入力と判断を UTC のタイムスタンプ付きでログに記録します。何か問題が起きたとき、何が起きたかを再現する唯一の手段がログです。リトライしたリクエストが誤って重複注文を作らないよう一意のクライアント注文IDを使い、ボットが把握しているポジションを取引所側のポジションと定期的に照合してください。

最小限のメインループで、各部品がどう組み合わさるかを示します。feed、strategy、broker の各オブジェクトは、自分で用意するデータ層、シグナル層、執行層のプレースホルダーです。

import logging

MAX_DAILY_LOSS = 300.0      # 口座通貨建て
MAX_POSITION = 2_000.0      # 銘柄ごとの想定元本（絶対値）

def run(feed, strategy, broker, dry_run=True):
    start_equity = broker.equity()
    for tick in feed:                                   # 例：WebSocket キューからのメッセージ
        pnl = broker.equity() - start_equity
        if pnl <= -MAX_DAILY_LOSS:
            logging.critical("Daily loss limit hit (%.2f). Stopping.", pnl)
            broker.cancel_all()
            broker.flatten()
            return                                      # キルスイッチ：人間による再開を待つ
        order = strategy.on_tick(tick)
        if order is None:
            continue
        new_pos = broker.position(order.symbol) + order.signed_notional
        if abs(new_pos) > MAX_POSITION:
            logging.warning("Order blocked by position limit: %s", order)
        elif dry_run:
            logging.info("DRY RUN, would send: %s", order)
        else:
            broker.send(order, client_order_id=order.uid)  # 一意のIDで重複を防ぐ

デプロイ

ボットは通常、取引所のサーバーに近いクラウドサーバーや VPS（仮想専用サーバー）で動かし、クラッシュ時には自動的に再起動するようにします。再起動の際、ボットはポジションがない状態から始まると仮定するのではなく、まず取引所から状態（未約定の注文、ポジション）を読み込まなければなりません。時刻を同期させ、メモリとディスクの使用量を監視し、取引所のメンテナンス時間に備えておいてください。

オープンソースのツール

多くのトレーダーは、ゼロから作るのではなく既存のライブラリを土台にしています。よく知られたオープンソースの例としては、CCXT（多数の暗号資産取引所APIを統一的に扱えるライブラリ）、Freqtrade と Hummingbot（暗号資産ボットのフレームワーク）、Backtrader と NautilusTrader（バックテストと取引のフレームワーク）、そして QuantConnect の LEAN エンジンがあります。これらは推奨ではなく例として挙げたものです。実際のお金で動かすコードは、必ず自分で確認してください。プラットフォーム別の解説については、Polymarket trading bot guideを参照してください。

計算例：レート制限とリスク予算

ある取引所では、1分あたりのリクエストウェイトの上限が1,200だとします（説明用の数字です。利用する取引所のドキュメントを確認してください）。ボットは10の市場を追跡しています。

  • 各市場の板をウェイト5で毎秒ポーリングすると、1分あたり 10 × 5 × 60 = 3,000 となり、上限の2.5倍です。ボットは利用を禁止されてしまいます。
  • マーケットデータを WebSocket のストリームに切り替えれば、これらのリクエストはなくなります。そのうえでボットが1分あたり約40件の注文を発注・取消し（各ウェイト1）、さらに1分に1回の残高確認（ウェイト10）を行うとすると、使用量は1分あたり約50で、予算の約4%です。

リスクについては、口座に10,000ドルがあるとします。ボットは1市場あたりのエクスポージャーを20%（2,000ドル）に制限し、1日の損失が3%（300ドル）に達したら取引を停止します。キルスイッチが作動する前にすべての保有ポジションが急激に逆行したとしても、最悪のケースは運ではなく、これらの上限と停止ロジックによって抑えられます。

よくある間違い

  • 再接続のロジックがない。 WebSocket のフィードは切断されるものです。黙って更新を止めたボットは、古い価格で取引してしまいます。
  • 注文が約定すると思い込む。 部分約定、拒否、取消を明示的に処理してください。
  • 冪等性なしでリトライする。 タイムアウトした注文が実は受け付けられている場合があり、再送するとポジションが2倍になることがあります。
  • 出金権限付きのキー。 サーバーが侵害されれば、そのまま全損につながります。
  • キルスイッチなしで実運用を始める。 バグは必ず発生します。バグの被害を無制限にするかどうかは選べます。
  • 穏やかな相場でしかテストしない。 値動きの激しい時期には、競合状態（レースコンディション）やレート制限の問題が表面化します。

よくある質問

トレーディングボットに最適なプログラミング言語は何ですか？

個人のボットでは、ライブラリの豊富さと使いやすさから Python が最も一般的な選択肢です。レイテンシーや非常に高いメッセージレートが重要な場合は、C++、Rust、Java などのより高速な言語が使われます。

トレーディングボットは儲かりますか？

ボットは戦略を自動化するだけで、エッジを生み出すわけではありません。多くのボットがお金を失うのは、元の戦略にコスト控除後のエッジがないか、ソフトウェアやリスク管理に不備があるためです。

トレーディングボットにAPIキーを渡しても安全ですか？

キーで資金を出金できず、既知のIPアドレスに制限され、資金に上限を設けたサブアカウントに限定されていれば、それなりに安全です。出金権限付きのキーやウォレットのシードフレーズは、絶対にサードパーティのサービスに渡さないでください。

アルゴリズム取引におけるキルスイッチとは何ですか？

キルスイッチとは、1日の損失や注文レートなどの上限を超えたときに、自動または手動で取引システムを停止し、注文を取り消し、設定されていればポジションを決済する制御機能です。

教育目的のコンテンツです。本サイトの内容は、金融・投資・法律・税務に関する助言ではありません。トレードには大きな損失リスクがあり、レバレッジ商品では入金額を超える損失が生じることがあります。ルール、手数料、プラットフォームの条件は変わります。取引の前に、ご利用の証券会社、取引所、規制当局で最新の条件をご確認ください。
