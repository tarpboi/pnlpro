트레이딩 봇은 브로커나 거래소에 연결해 시장 데이터를 읽고, 언제 매매할지 판단하고, 주문을 자동으로 보내는 프로그램입니다. 주문을 내는 봇을 만드는 것은 쉽습니다. 진짜 일은 데이터가 늦거나, 연결이 끊기거나, 전략이 오작동할 때도 안전하게 동작하는 봇을 만드는 것입니다. 이 글은 알고리즘 트레이딩의 엔지니어링 측면, 즉 표준 아키텍처, 거래소 API의 작동 방식, 그리고 실제 돈을 다루기 전에 모든 봇에 필요한 안전장치를 다룹니다.

핵심 요약

  • 봇을 데이터 피드, 신호, 리스크, 체결, 모니터링 계층으로 나누십시오.
  • 시장 데이터는 WebSocket 스트림으로 받고, REST 호출은 주문과 계좌 조회에만 쓰며, 호출 제한(rate limit)을 지키십시오.
  • API 키에는 꼭 필요한 최소 권한만 주고, 출금은 비활성화하며, 가능하면 IP 제한을 거십시오.
  • 하드 리스크 한도와 자동 킬 스위치는 선택이 아닙니다. 소프트웨어 장애는 어떤 나쁜 매매보다 빠르게 돈을 잃게 만들 수 있습니다.
  • 먼저 드라이런이나 모의매매 모드로 돌리고, 모든 것을 로그로 남기고, 실전 동작을 백테스트와 비교하십시오.

봇 아키텍처

단순한 스크립트부터 전문 시스템까지, 견고한 봇 대부분은 같은 구성 요소를 공유합니다.

계층 역할 핵심 고려 사항
데이터 피드 가격, 호가창, 체결, 계좌 업데이트 수신 재연결, 누락, 오래된 데이터, 타임스탬프
신호(전략) 데이터를 목표 포지션이나 주문으로 변환 백테스트와 같은 로직, 미래 참조 금지
리스크 주문이 나가기 전에 모든 주문을 한도와 대조 포지션 규모, 익스포저, 일일 손실, 가격 이상 여부 점검
체결 주문 제출·정정·취소, 체결 추적 멱등성, 부분 체결, 재시도, 호출 제한
상태와 저장소 포지션, 주문, 잔고를 일관되게 유지 거래소와 정기적으로 대사(reconcile)
모니터링 알림, 대시보드, 로그 문제가 생기면 몇 분 안에 알아차리기

계층을 분리해 두면 같은 신호 코드를 백테스트와 실전매매에 재사용할 수 있고, 리스크 계층을 따로 테스트할 수 있습니다. 리스크 계층은 전략이 무엇을 원하든 어떤 주문이든 막을 수 있어야 합니다. 체결 계층은 지정가 주문을 보내는 정도로 단순할 수도 있고, 집행 알고리즘에서 설명하는 주문 분할 로직처럼 복잡할 수도 있습니다.

거래소와 브로커 API

REST

REST API는 표준 웹 요청을 사용합니다. 요청(주문 제출, 잔고 조회)을 보내고 응답을 받습니다. 단순하지만 스트리밍 데이터에는 느리고, 요청 하나하나가 호출 제한에 포함됩니다.

WebSocket

WebSocket 연결은 열린 상태를 유지하면서 체결, 호가창 변화, 주문 체결 같은 업데이트를 발생 즉시 밀어 줍니다. 실시간 시장 데이터를 받는 표준 방식입니다. 봇은 연결 끊김을 처리하고, 다시 구독하고, 업데이트를 하나라도 놓치면 새 스냅샷으로 로컬 호가창을 다시 만들어야 합니다. 누락은 보통 시퀀스 번호로 감지합니다.

FIX

FIX 프로토콜은 기관 매매에서 오랫동안 쓰여 온 메시징 표준으로, 많은 브로커, 선물 회사, 일부 크립토 거래소가 주문 제출과 시장 데이터에 사용합니다. 구현은 더 복잡하지만, 세션이 안정적이고 메시지 빈도가 높을 때 오버헤드가 적습니다.

인증

프라이빗 엔드포인트는 보통 API 키와, 시크릿으로 계산한 서명(흔히 HMAC 기반), 그리고 타임스탬프를 요구합니다. 서버 시계가 어긋나면 요청이 거부될 수 있으므로 시스템 시계를 동기화해 두십시오. 블록체인 기반 크립토 거래소는 대신 지갑 개인 키로 주문에 서명하도록 요구하기도 합니다.

호출 제한

거래소는 초당 또는 분당 보낼 수 있는 요청 수를 제한하며, 무거운 요청일수록 많이 차감되는 "가중치(weight)" 예산 방식을 쓰는 경우가 많습니다. 한도를 넘으면 오류가 반환되고, 위반이 반복되면 일시적으로 차단됩니다. 좋은 관행은 다음과 같습니다.

  • REST 엔드포인트를 폴링하지 말고 WebSocket 스트림으로 시장 데이터를 받으십시오.
  • 토큰 버킷 카운터 등으로 자신의 사용량을 추적하고, 한도에 닿기 전에 속도를 늦추십시오.
  • 호출 제한 오류가 나면 즉시 재시도하지 말고 대기 시간을 점점 늘려 가며 물러나십시오(백오프).
  • 모든 주문을 한 번의 호출로 취소하는 것처럼, API가 지원하면 작업을 묶어서 처리하십시오.

API 키 보안

유출된 API 키 하나로 계좌가 텅 빌 수 있습니다. 키를 은행 비밀번호처럼 다루십시오.

  • 매매용 키는 출금을 비활성화하십시오. 봇이 자금을 출금해야 하는 경우는 거의 없습니다.
  • IP 주소로 제한하십시오. 그러면 키가 자신의 서버에서만 작동합니다.
  • 최소 권한 원칙을 지키십시오. 모니터링에는 읽기 전용 키를, 꼭 필요한 곳에만 매매 키를 쓰십시오.
  • 키를 코드나 공개 저장소에 절대 넣지 마십시오. 환경 변수나 시크릿 매니저에서 불러오십시오.
  • 거래소가 지원한다면 봇마다 자금이 제한된 서브 계정을 쓰십시오.
  • 출금 권한이 있는 키를 요구하는 서드파티 봇 서비스, 그리고 지갑 시드 문구를 요구하는 모든 도구를 경계하십시오. 크립토 지갑 보안을 참고하고, 텔레그램 방식의 스왑 봇은 밈코인 트레이딩 봇을 참고하십시오.

킬 스위치와 리스크 한도

소프트웨어 장애는 엄청난 결과를 낳을 수 있습니다. 2012년 8월 1일, 미국 마켓 메이커 Knight Capital은 결함 있는 코드를 배포했고, 이 코드가 의도하지 않은 주문을 쏟아 내 1시간도 안 되어 약 4억 4천만 달러를 잃었으며 회사는 구제를 받아야 하는 처지가 되었습니다. 주문을 계속 재전송하는 루프나 의도한 규모의 10배를 매매하는 단위 오류처럼, 같은 일의 소규모 버전은 개인 봇에서 늘 일어납니다.

모든 봇에는 다음이 있어야 합니다.

  • 종목별, 전체 기준의 최대 포지션 규모.
  • 최대 주문 규모와, 현재 시장가에서 멀리 떨어진 주문을 거부하는 가격 칼라(price collar).
  • 주문을 취소하고, 선택적으로 포지션을 정리하고, 사람이 다시 시작할 때까지 봇을 멈추는 일일 손실 한도.
  • 봇이 예상보다 훨씬 많은 주문을 보내면 멈추는 주문 빈도 한도.
  • 시장 데이터가 정해진 시간 동안 갱신되지 않으면 매매를 멈추는 오래된 데이터 점검.
  • 휴대폰에서 작동시킬 수 있는 수동 킬 스위치.

드라이런, 모의매매, 로깅

먼저 전체 시스템을 드라이런 모드로 돌리십시오. 이 모드에서는 주문을 계산해 로그만 남기고 실제로 보내지는 않습니다. 그다음 모의매매로, 또는 거래소 테스트넷이 있다면 테스트넷에서 돌리십시오. 테스트넷은 호가가 얇고 체결 방식이 다르는 등 실제 시장과 다르게 움직이는 경우가 많으므로, 성과 테스트가 아니라 소프트웨어 테스트로 여기십시오.

수신한 데이터, 신호, 보낸 주문, 거래소 응답, 체결, 오류 등 모든 입력과 결정을 UTC 타임스탬프와 함께 로그로 남기십시오. 문제가 생겼을 때 무슨 일이 있었는지 재구성할 수 있는 유일한 수단이 로그입니다. 재시도한 요청이 실수로 중복 주문을 만들지 않도록 고유한 클라이언트 주문 ID를 쓰고, 봇이 파악한 포지션을 거래소의 포지션과 정기적으로 대사하십시오.

최소한의 메인 루프로 각 부분이 어떻게 맞물리는지 보여 드립니다. feed, strategy, broker 객체는 각자의 데이터, 신호, 체결 계층을 대신하는 자리표시자입니다.

import logging

MAX_DAILY_LOSS = 300.0      # 계좌 통화 기준
MAX_POSITION = 2_000.0      # 종목당 명목금액 절댓값

def run(feed, strategy, broker, dry_run=True):
    start_equity = broker.equity()
    for tick in feed:                                   # 예: WebSocket 큐에서 받은 메시지
        pnl = broker.equity() - start_equity
        if pnl <= -MAX_DAILY_LOSS:
            logging.critical("Daily loss limit hit (%.2f). Stopping.", pnl)
            broker.cancel_all()
            broker.flatten()
            return                                      # 킬 스위치: 사람의 개입을 기다림
        order = strategy.on_tick(tick)
        if order is None:
            continue
        new_pos = broker.position(order.symbol) + order.signed_notional
        if abs(new_pos) > MAX_POSITION:
            logging.warning("Order blocked by position limit: %s", order)
        elif dry_run:
            logging.info("DRY RUN, would send: %s", order)
        else:
            broker.send(order, client_order_id=order.uid)  # 고유 ID로 중복 주문 방지

배포

봇은 보통 거래소 서버와 가까운 클라우드 서버나 가상 사설 서버(VPS)에서 돌리며, 크래시가 나면 자동으로 재시작하게 해 둡니다. 재시작할 때 봇은 포지션이 없는 상태에서 시작한다고 가정하지 말고, 먼저 거래소에서 상태(미체결 주문, 포지션)를 불러와야 합니다. 시계를 동기화하고, 메모리와 디스크 사용량을 모니터링하고, 거래소 점검 시간에 대비하십시오.

오픈소스 도구

많은 트레이더가 처음부터 만들지 않고 기존 라이브러리 위에 구축합니다. 잘 알려진 오픈소스 예로는 CCXT(여러 크립토 거래소 API를 통합한 라이브러리), Freqtrade와 Hummingbot(크립토 봇 프레임워크), Backtrader와 NautilusTrader(백테스트·매매 프레임워크), QuantConnect의 LEAN 엔진이 있습니다. 이는 추천이 아니라 예시로 언급한 것이며, 실제 돈으로 돌리는 코드는 무엇이든 직접 검토하십시오. 특정 플랫폼 기준의 안내는 Polymarket trading bot guide를 참고하십시오.

계산 예시: 호출 제한과 리스크 예산

어떤 거래소가 분당 요청 가중치 1,200을 허용한다고 합시다(설명용 수치이므로 이용하는 거래소의 문서를 확인하십시오). 봇은 10개 시장을 추적합니다.

  • 시장마다 매초 가중치 5짜리 호가창 폴링을 하면 분당 10 × 5 × 60 = 3,000으로, 한도의 2.5배입니다. 봇은 차단될 것입니다.
  • 시장 데이터를 WebSocket 스트림으로 바꾸면 이 요청들이 사라집니다. 그다음 봇이 분당 약 40건의 주문을 각각 가중치 1로 내거나 취소하고, 분당 한 번 가중치 10짜리 잔고 조회를 한다면 분당 약 50을 쓰게 되어 예산의 약 4% 수준입니다.

리스크 측면에서 계좌에 10,000달러가 있다고 합시다. 봇은 시장당 익스포저를 20%(2,000달러)로 제한하고, 일일 손실이 3%(300달러)에 이르면 매매를 멈춥니다. 킬 스위치가 작동하기 전에 열린 포지션 모두가 급격히 불리하게 움직이더라도, 최악의 경우는 운이 아니라 이 한도들과 중단 로직으로 제한됩니다.

흔한 실수

  • 재연결 로직이 없습니다. WebSocket 피드는 끊깁니다. 조용히 업데이트가 멈춘 봇은 오래된 가격으로 매매합니다.
  • 주문이 체결된다고 가정합니다. 부분 체결, 거부, 취소를 명시적으로 처리하십시오.
  • 멱등성 없이 재시도합니다. 타임아웃된 주문도 이미 접수되었을 수 있으며, 다시 보내면 포지션이 두 배가 될 수 있습니다.
  • 출금 권한이 있는 키를 씁니다. 서버가 한 번 뚫리면 전액 손실로 이어집니다.
  • 킬 스위치 없이 실전에 들어갑니다. 버그는 반드시 생깁니다. 버그의 피해를 무한정으로 둘지는 선택의 문제입니다.
  • 조용한 시장에서만 테스트합니다. 변동성이 큰 구간에서 경쟁 상태(race condition)와 호출 제한 문제가 드러납니다.

자주 묻는 질문

트레이딩 봇에 가장 좋은 프로그래밍 언어는 무엇인가요?

라이브러리가 풍부하고 쓰기 쉬워서 개인용 봇에는 Python이 가장 흔한 선택입니다. 지연시간이나 매우 높은 메시지 빈도가 중요할 때는 C++, Rust, Java 같은 더 빠른 언어를 씁니다.

트레이딩 봇으로 수익을 낼 수 있나요?

봇은 전략을 자동화할 뿐 엣지를 만들어 내지는 않습니다. 기반 전략에 비용 차감 후 엣지가 없거나, 소프트웨어와 리스크 관리에 실패해서 돈을 잃는 봇이 많습니다.

트레이딩 봇에 API 키를 줘도 안전한가요?

키로 출금이 불가능하고, 알려진 IP 주소로 제한되어 있으며, 자금 한도가 정해진 서브 계정으로 제한된다면 상당히 안전할 수 있습니다. 출금 권한이 있는 키나 지갑 시드 문구는 절대 서드파티 서비스와 공유하지 마십시오.

알고리즘 트레이딩에서 킬 스위치란 무엇인가요?

킬 스위치는 일일 손실이나 주문 빈도 같은 한도를 넘었을 때 자동 또는 수동으로 매매 시스템을 멈추고, 주문을 취소하고, 설정에 따라 포지션까지 청산하는 통제 장치입니다.

교육 목적의 콘텐츠입니다. 이곳의 어떤 내용도 금융, 투자, 법률 또는 세무 조언이 아닙니다. 트레이딩은 손실 위험이 크며, 레버리지 상품은 입금액보다 큰 손실이 날 수 있습니다. 규칙, 수수료, 플랫폼 조건은 바뀔 수 있으니 거래 전에 브로커, 거래소 또는 감독기관에서 최신 조건을 확인하십시오.
