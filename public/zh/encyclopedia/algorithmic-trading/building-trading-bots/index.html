交易机器人（trading bot）是一种连接券商或交易所、读取市场数据、决定何时交易并自动发送订单的程序。写一个能下单的机器人很容易；真正的功夫在于让它在数据延迟、连接中断或策略出错时仍能安全运行。这是算法交易的工程层面：标准架构、交易所 API 的工作方式，以及每个机器人在接触真金白银之前都必须具备的安全控制。

核心要点

  • 把机器人分成几层：数据源、信号、风控、执行和监控。
  • 用 WebSocket 推送接收行情数据，REST 调用只留给下单和账户查询，并保持在频率限制之内。
  • API 密钥只应授予所需的最小权限，关闭提币权限，并在可能时设置 IP 限制。
  • 硬性风险限额和自动紧急停止开关不是可选项；软件故障亏钱的速度可能比任何一笔坏交易都快。
  • 先在空跑或模拟模式下运行，记录一切日志，并把实盘表现与回测进行比较。

机器人架构

从简单脚本到专业系统，大多数稳健的机器人都由相同的模块构成。

层 职责 关键关注点
数据源 接收价格、订单簿、成交和账户更新 重连、数据缺口、过期数据、时间戳
信号（策略） 把数据转化为目标仓位或订单 与回测逻辑一致；不能有前视偏差
风控 每笔订单发出前都要对照限额检查 仓位规模、风险敞口、单日亏损、价格合理性检查
执行 下单、改单和撤单；跟踪成交 幂等性、部分成交、重试、频率限制
状态与存储 保持仓位、订单和余额一致 定期与交易所对账
监控 警报、仪表盘、日志 出问题时几分钟内就能知道

各层分离意味着你可以在回测和实盘中复用同一套信号代码，也可以单独测试风控层。无论策略想做什么，风控层都应能拦截任何订单。执行层可以简单到只发限价单，也可以复杂到采用执行算法中介绍的拆单逻辑。

交易所与券商 API

REST

REST API 使用标准的网络请求。你发送一个请求（下单、查询余额），然后收到响应。它简单易用，但用来获取流式数据太慢，而且每个请求都会计入频率限制。

WebSocket

WebSocket 连接保持打开状态，并在事件发生时向你推送更新：成交、订单簿变化、订单成交回报。它是实时接收行情数据的标准方式。机器人必须处理断线、重新订阅，并在漏掉任何更新时（通常通过序列号检测）根据新的快照重建本地订单簿。

FIX

FIX 协议是机构交易中历史悠久的消息标准，许多券商、期货公司和部分加密货币交易平台都用它来下单和传输行情数据。它的实现更复杂，但会话稳定，在高消息速率下开销更低。

身份验证

私有接口通常需要一个 API 密钥，以及用密钥（secret）计算出的签名（多为基于 HMAC 的签名）和时间戳。如果服务器时钟漂移，请求可能会被拒绝，因此要保持系统时钟同步。基于区块链的加密货币交易平台则可能要求用钱包私钥对订单签名。

频率限制

交易所会限制你每秒或每分钟可发送的请求数，通常以“权重”预算的形式实现，较重的请求消耗更多权重。超出限制会返回错误，屡次违规还会被临时封禁。良好的做法：

  • 从 WebSocket 推送获取行情数据，而不是轮询 REST 接口。
  • 自行跟踪用量，常用令牌桶计数器，在触及限制之前就放慢速度。
  • 遇到频率限制错误时，以逐步增加的延迟退避，而不是立即重试。
  • 在 API 支持的情况下批量操作，例如一次调用撤销所有订单。

API 密钥安全

泄露的 API 密钥可能让账户被掏空。要像对待银行密码一样对待密钥：

  • 关闭交易密钥的提币权限。 机器人很少需要提取资金。
  • 按 IP 地址限制， 让密钥只能从你的服务器使用。
  • 遵循最小权限原则： 监控用只读密钥，只在必要的地方使用交易密钥。
  • 绝不要把密钥写进代码或公开代码仓库。从环境变量或密钥管理器中加载。
  • 在交易平台支持的情况下，为每个机器人使用一个资金有限的子账户。
  • 警惕要求提供带提币权限密钥的第三方机器人服务，以及任何索要钱包助记词的工具。参见加密钱包安全；关于 Telegram 类兑换机器人，参见meme 币交易机器人。

紧急停止开关与风险限额

软件故障可能造成惊人的后果。2012年8月1日，美国做市商 Knight Capital 部署了有缺陷的代码，发出大量意外订单，在不到一小时内亏损约4.4亿美元，公司不得不接受救助。同类事故的小型版本，比如反复重发订单的循环，或单位错误导致按预期规模的十倍交易，在散户机器人身上屡见不鲜。

每个机器人都应具备：

  • 最大仓位，按单个品种和整体分别设置。
  • 最大单笔订单规模，以及拒绝偏离当前市价过远订单的价格保护带。
  • 单日亏损限额，触发后撤销订单、可选择平掉所有仓位，并停止机器人，直到有人手动重启。
  • 下单频率限制，当机器人发出的订单远多于预期时将其停止。
  • 过期数据检查，行情数据在设定时间内未更新就停止交易。
  • 手动紧急停止开关，可以用手机触发。

空跑、模拟交易与日志

先让整个系统在空跑（dry-run）模式下运行，即只计算订单并记录日志而不实际发送；然后在模拟交易中运行，或在交易所提供测试网时在测试网上运行。测试网的表现往往与实盘市场不同，订单簿更薄、成交也不同，因此要把它当作软件测试，而不是业绩测试。

记录每一项输入和决策：收到的数据、信号、发出的订单、交易所的响应、成交和错误，全部带 UTC 时间戳。出问题时，日志是重现事件经过的唯一途径。使用唯一的客户端订单 ID，确保重试请求不会意外产生重复订单，并定期将机器人记录的仓位与交易所的仓位对账。

下面这个最简主循环展示了各部分如何配合。feed、strategy 和 broker 对象是占位符，分别代表你自己的数据层、信号层和执行层。

import logging

MAX_DAILY_LOSS = 300.0      # 账户计价货币
MAX_POSITION = 2_000.0      # 每个品种的名义金额绝对值上限

def run(feed, strategy, broker, dry_run=True):
    start_equity = broker.equity()
    for tick in feed:                                   # 例如来自 WebSocket 队列的消息
        pnl = broker.equity() - start_equity
        if pnl <= -MAX_DAILY_LOSS:
            logging.critical("Daily loss limit hit (%.2f). Stopping.", pnl)
            broker.cancel_all()
            broker.flatten()
            return                                      # 紧急停止：等待人工处理
        order = strategy.on_tick(tick)
        if order is None:
            continue
        new_pos = broker.position(order.symbol) + order.signed_notional
        if abs(new_pos) > MAX_POSITION:
            logging.warning("Order blocked by position limit: %s", order)
        elif dry_run:
            logging.info("DRY RUN, would send: %s", order)
        else:
            broker.send(order, client_order_id=order.uid)  # 唯一 ID 防止重复下单

部署

机器人通常运行在靠近交易所服务器的云服务器或虚拟专用服务器（VPS）上，并在崩溃时自动重启。重启时，机器人必须先从交易所加载状态（挂单、仓位），而不是假设自己从空仓开始。保持时钟同步，监控内存和磁盘使用情况，并为交易所的维护窗口做好预案。

开源工具

许多交易者在现有库的基础上开发，而不是从零开始。知名的开源项目包括 CCXT（统一对接众多加密货币交易所 API 的库）、Freqtrade 和 Hummingbot（加密货币机器人框架）、Backtrader 和 NautilusTrader（回测与交易框架），以及 QuantConnect 的 LEAN 引擎。这里只是举例，而非推荐；任何要用真金白银运行的代码都要亲自审查。针对特定平台的详细教程，参见Polymarket 交易机器人指南。

实例：频率限制与风险预算

某交易所允许每分钟1,200的请求权重（这是示意数字，请查阅你所用平台的文档）。一个机器人跟踪10个市场。

  • 每秒轮询一次每个市场的订单簿、每次权重为5，每分钟消耗10 × 5 × 60 = 3,000，是限额的2.5倍。机器人会被封禁。
  • 把行情数据切换到 WebSocket 推送后，这些请求就没有了。如果机器人随后每分钟下单或撤单约40次、每次权重为1，再加上每分钟一次权重为10的余额查询，每分钟约消耗50，约占预算的4%。

在风险方面，账户有10,000美元。机器人把每个市场的风险敞口上限设为20%（2,000美元），单日亏损达3%（300美元）时停止交易。即使在紧急停止开关触发前所有持仓都剧烈不利，最坏情况也受这些限额和止损逻辑的约束，而不是靠运气。

常见错误

  • 没有重连逻辑。 WebSocket 数据流会断开；默默停止更新的机器人会按过期价格交易。
  • 假设订单一定成交。 要明确处理部分成交、拒单和撤单。
  • 重试时不保证幂等性。 超时的订单可能其实已被接受；重新发送可能让仓位翻倍。
  • 密钥带有提币权限。 这会让任何一次服务器入侵都变成全部损失。
  • 没有紧急停止开关就上实盘。 Bug 必然存在；但 Bug 造成的损失是否无上限，取决于你。
  • 只在平静的市场中测试。 剧烈波动的时期会暴露竞态条件和频率限制问题。

常见问题

交易机器人用哪种编程语言最好？

Python 凭借丰富的库和易用性，是散户机器人最常见的选择。当延迟或极高的消息速率很重要时，会使用 C++、Rust 或 Java 等更快的语言。

交易机器人能赚钱吗？

机器人只是把策略自动化，并不会创造优势。许多机器人亏钱，是因为底层策略扣除成本后没有优势，或者因为软件和风控出了故障。

把 API 密钥交给交易机器人安全吗？

如果密钥无法提币、仅限已知 IP 地址使用，并且限定在资金有上限的子账户中，那么可以算是相当安全。绝不要把带提币权限的密钥或钱包助记词交给第三方服务。

算法交易中的紧急停止开关是什么？

紧急停止开关（kill switch）是一种控制机制：当单日亏损或下单频率等限额被突破时，自动或手动停止交易系统、撤销其订单，并在已配置的情况下平掉仓位。
