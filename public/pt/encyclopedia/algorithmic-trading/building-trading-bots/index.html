Como criar robôs de trading

Um robô de trading (trading bot) é um programa que se conecta a uma corretora ou exchange, lê dados de mercado, decide quando operar e envia ordens automaticamente. Construir um robô que envia uma ordem é fácil; construir um que se comporte com segurança quando os dados atrasam, a conexão cai ou a estratégia falha é que dá trabalho de verdade. Este é o lado de engenharia do trading algorítmico: a arquitetura padrão, como funcionam as APIs das exchanges e os controles de segurança de que todo robô precisa antes de tocar em dinheiro real.

Principais pontos

  • Divida o robô em camadas: feed de dados, sinal, risco, execução e monitoramento.
  • Use streams WebSocket para os dados de mercado e reserve as chamadas REST para ordens e consultas de conta, respeitando os rate limits.
  • As API keys devem ter apenas as permissões mínimas necessárias, com saques desativados e restrição de IP onde houver.
  • Limites rígidos de risco e um kill switch automático não são opcionais; falhas de software podem perder dinheiro mais rápido que qualquer operação ruim.
  • Rode primeiro em modo dry run ou paper trading, registre tudo em log e compare o comportamento ao vivo com o seu backtest.

Arquitetura do robô

A maioria dos robôs robustos, de scripts simples a sistemas profissionais, compartilha os mesmos blocos.

Camada Função Principais cuidados
Feed de dados Receber preços, livros de ofertas, negócios e atualizações da conta Reconexão, lacunas, dados defasados, timestamps
Sinal (estratégia) Transformar dados em posições ou ordens desejadas A mesma lógica do backtest; sem look-ahead
Risco Conferir cada ordem contra os limites antes que ela saia Tamanho de posição, exposição, perda diária, checagens de sanidade de preço
Execução Enviar, alterar e cancelar ordens; acompanhar as execuções Idempotência, execuções parciais, novas tentativas, rate limits
Estado e armazenamento Manter posições, ordens e saldos consistentes Conciliar com a exchange regularmente
Monitoramento Alertas, painéis, logs Saber em minutos quando algo está errado

Manter as camadas separadas significa que você pode reaproveitar o mesmo código de sinal no backtesting e na operação real, e pode testar a camada de risco isoladamente. A camada de risco deve ser capaz de bloquear qualquer ordem, não importa o que a estratégia queira. A camada de execução pode ser tão simples quanto enviar ordens limitadas ou tão elaborada quanto a lógica de fatiamento descrita em algoritmos de execução.

APIs de exchanges e corretoras

REST

As APIs REST usam requisições web padrão. Você envia uma requisição (enviar uma ordem, consultar saldos) e recebe uma resposta. São simples, mas lentas para dados em streaming, e cada requisição conta para um rate limit.

WebSocket

As conexões WebSocket ficam abertas e enviam as atualizações para você à medida que acontecem: negócios, mudanças no livro de ofertas, execuções de ordens. São a forma padrão de receber dados de mercado em tempo real. O robô precisa lidar com desconexões, refazer as inscrições e reconstruir o livro de ofertas local a partir de um snapshot novo se alguma atualização for perdida, o que normalmente se detecta pelos números de sequência.

FIX

O protocolo FIX é o padrão de mensagens consolidado há muito tempo no trading institucional, usado por muitas corretoras, empresas de futuros e algumas plataformas de cripto para envio de ordens e dados de mercado. É mais complexo de implementar, mas oferece sessões estáveis e menor overhead para altas taxas de mensagens.

Autenticação

Os endpoints privados normalmente exigem uma API key e uma assinatura calculada com um segredo, muitas vezes baseada em HMAC, além de um timestamp. Se o relógio do seu servidor se desviar, as requisições podem ser rejeitadas, então mantenha o relógio do sistema sincronizado. Plataformas de cripto construídas sobre blockchains podem, em vez disso, exigir que as ordens sejam assinadas com a chave privada de uma carteira.

Rate limits

As exchanges limitam quantas requisições você pode enviar por segundo ou por minuto, muitas vezes na forma de um orçamento de "peso" (weight), em que requisições pesadas custam mais. Ultrapassar o limite gera erros e, em caso de violações repetidas, bloqueios temporários. Boas práticas:

  • Obtenha os dados de mercado por streams WebSocket em vez de fazer polling nos endpoints REST.
  • Acompanhe o seu próprio consumo, muitas vezes com um contador do tipo token bucket, e desacelere antes de atingir o limite.
  • Ao receber um erro de rate limit, recue com atrasos crescentes (backoff) em vez de tentar de novo imediatamente.
  • Agrupe operações quando a API permitir, como cancelar todas as ordens em uma única chamada.

Segurança das API keys

Uma API key vazada pode esvaziar uma conta. Trate as chaves como as senhas do seu banco:

  • Desative os saques nas chaves de trading. Um robô raramente precisa sacar recursos.
  • Restrinja por endereço IP para que a chave só funcione a partir do seu servidor.
  • Use o menor privilégio possível: chaves somente leitura para monitoramento, chaves de trading só onde for necessário.
  • Nunca coloque chaves no código nem em repositórios públicos. Carregue-as de variáveis de ambiente ou de um gerenciador de segredos.
  • Use uma subconta com recursos limitados para cada robô, quando a plataforma permitir.
  • Desconfie de serviços de robôs de terceiros que pedem chaves com permissão de saque e de qualquer ferramenta que peça a seed phrase de uma carteira. Veja segurança de carteiras de cripto e, para robôs de swap no estilo Telegram, robôs de trading de meme coins.

Kill switches e limites de risco

Falhas de software podem ser espetaculares. Em 1º de agosto de 2012, o market maker americano Knight Capital colocou em produção um código com defeito que disparou uma enxurrada de ordens não intencionais, perdendo cerca de 440 milhões de dólares em menos de uma hora e levando a empresa a precisar de um resgate. Versões menores da mesma coisa, como um loop que reenvia ordens ou um erro de unidade que opera dez vezes o tamanho pretendido, acontecem com robôs de varejo o tempo todo.

Todo robô deve ter:

  • Tamanho máximo de posição por instrumento e no total.
  • Tamanho máximo de ordem e um colar de preço que rejeite ordens muito distantes do mercado atual.
  • Limite de perda diária que cancele as ordens, opcionalmente zere as posições e pare o robô até que um humano o reinicie.
  • Limite de taxa de ordens que pare o robô se ele enviar muito mais ordens do que o esperado.
  • Checagem de dados defasados que interrompa as operações se os dados de mercado não forem atualizados por um tempo definido.
  • Um kill switch manual que você possa acionar pelo celular.

Dry run, paper trading e logs

Rode primeiro o sistema completo em modo dry run, em que ele calcula as ordens e as registra em log sem enviá-las, e depois em paper trading ou na testnet da exchange, quando houver. As testnets muitas vezes se comportam de forma diferente dos mercados reais, com livros mais rasos e execuções diferentes, então trate-as como um teste de software, não como um teste de desempenho.

Registre em log cada entrada e cada decisão: dados recebidos, sinais, ordens enviadas, respostas da exchange, execuções e erros, tudo com timestamps em UTC. Quando algo dá errado, os logs são a única forma de reconstruir o que aconteceu. Use client order IDs únicos para que uma requisição repetida não crie por acidente uma ordem duplicada, e concilie regularmente a visão de posições do seu robô com a da exchange.

Um loop principal mínimo mostra como as peças se encaixam. Os objetos feed, strategy e broker são marcadores para as suas próprias camadas de dados, sinal e execução.

import logging

MAX_DAILY_LOSS = 300.0      # moeda da conta
MAX_POSITION = 2_000.0      # nocional absoluto por símbolo

def run(feed, strategy, broker, dry_run=True):
    start_equity = broker.equity()
    for tick in feed:                                   # p. ex. mensagens de uma fila WebSocket
        pnl = broker.equity() - start_equity
        if pnl <= -MAX_DAILY_LOSS:
            logging.critical("Daily loss limit hit (%.2f). Stopping.", pnl)
            broker.cancel_all()
            broker.flatten()
            return                                      # kill switch: aguarda um humano
        order = strategy.on_tick(tick)
        if order is None:
            continue
        new_pos = broker.position(order.symbol) + order.signed_notional
        if abs(new_pos) > MAX_POSITION:
            logging.warning("Order blocked by position limit: %s", order)
        elif dry_run:
            logging.info("DRY RUN, would send: %s", order)
        else:
            broker.send(order, client_order_id=order.uid)  # ID único evita duplicatas

Implantação

Os robôs normalmente rodam em um servidor na nuvem ou em um servidor virtual privado (VPS) perto dos servidores da exchange, com reinício automático em caso de falha. Ao reiniciar, o robô deve primeiro carregar o seu estado a partir da exchange (ordens abertas, posições) em vez de supor que começa zerado. Mantenha o relógio sincronizado, monitore o uso de memória e de disco e planeje-se para as janelas de manutenção da exchange.

Ferramentas open source

Muitos traders constroem sobre bibliotecas existentes em vez de começar do zero. Exemplos open source conhecidos incluem CCXT (uma biblioteca unificada para as APIs de muitas exchanges de cripto), Freqtrade e Hummingbot (frameworks de robôs de cripto), Backtrader e NautilusTrader (frameworks de backtesting e trading) e o motor LEAN da QuantConnect. Eles são citados como exemplos, não como recomendações; revise qualquer código que você rode com dinheiro real. Para um passo a passo específico de plataforma, veja o guia de robô de trading na Polymarket.

Exemplo prático: rate limit e orçamento de risco

Uma exchange permite um peso de requisições de 1,200 por minuto (um número ilustrativo; consulte a documentação da sua plataforma). Um robô acompanha 10 mercados.

  • Fazer polling do livro de ofertas de cada mercado a cada segundo, com peso 5, custa 10 × 5 × 60 = 3,000 por minuto, 2.5 vezes o limite. O robô seria bloqueado.
  • Passar os dados de mercado para streams WebSocket elimina essas requisições. Se o robô então enviar ou cancelar cerca de 40 ordens por minuto com peso 1 cada, mais uma consulta de saldo por minuto com peso 10, ele usa cerca de 50 por minuto, por volta de 4% do orçamento.

Quanto ao risco, a conta tem 10,000 dólares. O robô limita a exposição a 20% por mercado (2,000 dólares) e para de operar com uma perda diária de 3% (300 dólares). Mesmo que todas as posições abertas andassem fortemente contra ele antes de o kill switch disparar, o pior caso fica limitado por esses limites e pela lógica de parada, e não pela sorte.

Erros comuns

  • Sem lógica de reconexão. Feeds WebSocket caem; um robô que para de se atualizar em silêncio opera com preços defasados.
  • Supor que as ordens são executadas. Trate explicitamente execuções parciais, rejeições e cancelamentos.
  • Repetir tentativas sem idempotência. Uma ordem que deu timeout pode ainda assim ter sido aceita; reenviá-la pode dobrar a posição.
  • Chaves com permissão de saque. Isso transforma qualquer invasão do servidor em perda total.
  • Ir para o real sem kill switch. Bugs são certos; bugs sem limite são opcionais.
  • Testar só em mercados calmos. Períodos voláteis expõem condições de corrida e problemas de rate limit.

Perguntas frequentes

Qual é a melhor linguagem de programação para um robô de trading?

Python é a escolha mais comum para robôs de varejo, por causa das bibliotecas e da facilidade de uso. Linguagens mais rápidas, como C++, Rust ou Java, são usadas quando a latência ou taxas de mensagens muito altas importam.

Robôs de trading dão lucro?

Um robô apenas automatiza uma estratégia; ele não cria vantagem. Muitos robôs perdem dinheiro porque a estratégia por trás não tem vantagem depois dos custos, ou por falhas de software e de controle de risco.

É seguro dar a minha API key a um robô de trading?

Pode ser razoavelmente seguro se a chave não puder sacar recursos, estiver restrita a endereços IP conhecidos e limitada a uma subconta com recursos limitados. Nunca compartilhe chaves com permissão de saque nem seed phrases de carteira com serviços de terceiros.

O que é um kill switch no trading algorítmico?

Um kill switch é um controle que, de forma automática ou manual, para um sistema de trading, cancela suas ordens e, se configurado, encerra as posições quando limites como a perda diária ou a taxa de ordens são ultrapassados.

Conteúdo apenas educativo. Nada aqui é recomendação financeira, de investimento, jurídica ou tributária. Operar envolve alto risco de perda, e com produtos alavancados você pode perder mais do que depositou. Regras, taxas e condições das plataformas mudam: confira os termos atuais com sua corretora, exchange ou regulador antes de operar.
